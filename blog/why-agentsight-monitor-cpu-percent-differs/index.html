Why AgentSight monitor CPU% and CPU milliseconds can disagree

In the v1.0.35 background monitor, cpu_ms represents sampled CPU-time increments, while cpu_percent estimates a rate against wall time. They are not two units for the same number. Their first-sample behavior differs, and the percentage calculation does not apply the same process-start identity guard used by the CPU-millisecond delta.

Direct answer: compare CPU time and CPU rate only on a common interval

The monitor records a monitor_windows.cpu_ms aggregate by summing per-process process_cpu_ms_delta over the matched process family. The detailed process_samples.cpu_percent field instead calls process_cpu_percent, converting accumulated CPU ticks into a rate relative to elapsed monotonic wall time. Both depend on snapshots; neither is a kernel event ledger for every instruction executed by an agent.

This is a source audit of AgentSight v1.0.35 at commit c1574366122a90c451bca6a84713e28813ab95e2, not a new runtime benchmark. The calculation is especially important when a new process enters a sampled family, a short-lived subprocess falls between samples, or process IDs are reused.

The existing background monitoring guide owns the cadence and database architecture. This page covers the distinct engineering question of how to interpret the numeric resource fields and detect incomparable baselines.

Follow the two different CPU formulas

The process snapshot is built with sysinfo process data. Accumulated CPU milliseconds are converted to ticks using the platform clock-tick rate. For a process seen in both snapshots with matching starttime_ticks, process_cpu_ms_delta subtracts ticks, converts back to milliseconds, and rounds. When either the previous snapshot or matching process identity is missing, it returns zero.

For CPU percentage, process_cpu_percent looks up the old process by PID and divides the nonnegative difference in CPU ticks by measured elapsed wall time, then multiplies by 100. It does not normalize by host CPU count. A multithreaded process can therefore exceed 100%.

cpu_ms ~= round(delta_cpu_ticks / clock_ticks_per_second * 1000)
cpu_percent ~= (delta_cpu_ticks / clock_ticks_per_second) / delta_wall_seconds * 100

The code paths diverge when no previous PID row exists. CPU milliseconds return zero, while CPU percentage falls back to lifetime average CPU use: accumulated ticks divided by elapsed process age (with a minimum age of 0.001 seconds). That rate is not directly comparable with an adjacent two-second CPU-time delta. The precise measurement window also depends on the real snapshot timestamps, not just the configured loop interval.

A subtle identity mismatch: PID reuse

The v1.0.35 CPU-millisecond delta explicitly rejects a previous PID whose starttime_ticks differs from the current process. The read/write byte-delta path is even more explicit: its prior-state map uses a ProcessKey composed of PID and start time.

The percentage function only checks that the previous snapshot contains the same numeric PID. If that PID was recycled for another process, its accumulated CPU ticks can be subtracted from the new occupant. A lower current counter is clamped to zero by saturating_sub; a higher current counter may produce a nonrepresentative rate. This is a code-level corner casedemonstrated by the guard mismatch, not evidence that a particular production run was affected. A safe downstream comparison keys process observations by PID and start time.

Memory and I/O tell different stories again

The monitor converts each process RSS into bytes and adds those values across the matched process family. This is useful for locating a large family, but shared resident pages can be represented in multiple per-process RSS numbers. The summed rss_bytes is therefore not a precise unique-physical- memory measurement or a cgroup memory-usage counter.

Monitor read_bytes and write_bytes come from sampled process disk-usage counters. The monitor stores saturating differences between consecutive observations keyed by PID and start time. A process first seen on the current tick gets zero delta; that does not establish no I/O since process launch. These fields also do not represent every file operation, read syscall, or network byte transferred.

Per-session aggregate windows are written on the two-second monitor loop. Persisted process detail is selected only at 30-second crossings. If there are more than ten processes, the retained detail selects up to five highest and five lowest by a score ordered by CPU milliseconds, RSS, then I/O. It is not a complete inventory and is not sorted primarily by CPU%.

Reproduce the source inspection

These commands inspect the exact released implementation; they do not launch a monitor, read private session artifacts, or assume synthetic values were measured. Run them in a local checkout of the AgentSight product repository.

git checkout c1574366122a90c451bca6a84713e28813ab95e2
grep -n -E "fn process_cpu_percent|fn process_cpu_ms_delta|starttime_ticks|delta_wall" agentsight-capture/src/sources/proc.rs
grep -n -E "MONITOR_INTERVAL_SECS|DETAIL_SAMPLE_INTERVAL_SECS|fn aggregate_process_samples|fn process_io_delta|fn bounded_process_samples" collector/src/cmd_monitor.rs
grep -n -E "monitor_windows|process_samples|cpu_percent|rss_bytes" collector/src/cmd_monitor.rs

To evaluate an actual resource hotspot, compare consecutive complete snapshots for the same (pid, starttime_ticks), inspect elapsed wall time, and distinguish short-lived descendants from the currently sampled family. Preserve a provider-native agent timeline if you need to attribute the workload to a prompt or tool decision. A high CPU% does not identify which agent instruction caused the load.
