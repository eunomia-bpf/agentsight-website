Why pathname syscall probes can miss events even when they are attached

An attached BPF program is not the same as an observed syscall. A filesystem SUMMARY can be absent because the selected tracepoint did not invoke the program, the syscall or process was excluded, a user pathname was unreadable, or an aggregate never reached output. AgentSight master commit fbc6d91achanged pathname hooks from individual syscalls:sys_enter_*events to a raw_syscalls:sys_enter dispatcher after an observed CI case with silent path hooks. Diagnose each gate; do not infer a successful file mutation from either hook.

What failed, and what is actually established?

The November 21 product change describes CI runs in which the per-syscall pathname programs were entered zero times, while file-descriptor-oriented write and truncate tracing still produced summaries. That is a source-reported CI observation, not a benchmark repeated independently for this article. The change replaces seven pathname entry programs with one raw syscall entry program, while keeping separate non-path hooks such as ftruncate. The root-only regression fixture subsequently requires DIR_CREATE, WRITE, FILE_RENAME, and FILE_DELETE summary types.

The implementation here is unreleased master at fbc6d91a025b561970f6e526a5c77bb07754f30a. The latest stable binary reviewed is v1.0.35 from October 23, which predates the switch. Do not apply this source contract to a stable installation without checking its actual BPF object and build revision.

Five gates between syscall and SUMMARY

GatePositive evidenceWhat remains unknown
AttachmentExpected BPF link exists; tracepoint enabledNeither condition proves the hook ran for the target syscall
Tracepoint deliveryPer-syscall or raw sys_enter callback executesA syscall in strace is not evidence that this BPF callback ran
Dispatcher and scopeArchitecture-specific syscall ID is selected and PID passes trackingAn unsupported ID or unrelated process can be correctly discarded
User path readbpf_probe_read_user_str copies pathname or records read errorAn unreadable argument does not identify the target path
Aggregation and flushKey reaches map and is emitted as SUMMARYA missing output line alone does not locate which prior stage failed

This order matters. A live link ID tells you only that a link exists. A syscall observed by a separate tool tells you only that the workload issued it. Neither confirms the BPF entry program ran, its process filter accepted the event, or the aggregate was subsequently flushed. The master FS_LINK_INFOdiagnostic prints link and tracepoint-enable information, not per-hook execution counts.

Why use the raw syscall tracepoint?

Per-syscall tracepoints carry syscall-specific formatting and can involve kernel-side user-argument handling before the event reaches some consumers. In the observed AgentSight test environment, the older pathname hooks were silent. The new raw_syscalls:sys_enter event exposes the syscall number and six raw arguments, permitting a single BPF program to dispatch without requiring the per-syscall pathname event. The BPF program still reads the user pathname itself; switching tracepoints does not make a bad pointer readable.

Kernel-version caveat: the product change attributes the CI failure to kernel syscall tracing faultable user-copy handling. The independently inspected Linux trace_syscalls.c snapshot at 4843f687 has check_faultable_syscall and user-argument buffering, but its perf_syscall_enter explicitly invokes the BPF callback before allocating or populating the perf event buffer. Consequently that code snapshot alone does notestablish that a failed pathname copy prevents the BPF callback on every kernel. Preserve the original CI observation, record the running kernel revision, and avoid treating the proposed cause as a universal law.

What does the raw dispatcher actually recognize?

The BPF source uses compile-time architecture selection and literal syscall IDs. Paths are read from fixed argument offsets, because computed indexing into the tracepoint context ran into BPF verifier pointer constraints. Other IDs return immediately. This is a finite set of pathname operations, not a generic filesystem audit.

For rename calls the dispatcher captures the destinationpathname, not the original one. It observes syscall entry, not completion or return status. The relatedfilesystem SUMMARY evidence guide covers the separate question of grouping, counts and whether a file really changed.

A reproducible debugging sequence

Start with a disposable Linux test directory and matching source revision. The commands below inspect the implementation and the kernel environment; the test itself requires root, a built process tracer, and an available eBPF kernel. Do not treat a passing upstream fixture on one CI kernel as a guarantee of coverage on other kernels.

git clone https://github.com/eunomia-bpf/agentsight.git
cd agentsight
git checkout fbc6d91a025b561970f6e526a5c77bb07754f30a
uname -r
rg -n "trace_raw_path|__TARGET_ARCH" bpf/process_ext/bpf_fs.h
rg -n "FS_LINK_INFO|AGG_MAP_COUNTS|flush_agg_map" bpf/process.c
rg -n "test_trace_fs_summary_events|PROBE_ENV" bpf/tests/test_process_runtime.py
# With a correctly built process tracer and test prerequisites:
cd bpf
sudo python3 tests/test_process_runtime.py

Compare the actual syscall variant and target architecture with the selected IDs. Confirm --trace-fs and process tracking scope. Separately inspect BPF link presence, tracepoint enable state, map overflow and flush evidence, and the emitted SUMMARY types. The fixture exercises direct x86 syscall IDs and records kernel/glibc diagnostics; on another architecture its hard-coded direct calls require adaptation. Do not run tracing tests against private production sessions merely to validate a website claim.

Another diagnostic caveat in this pinned master revision:FS_LINK_INFO rows marked phase="exit"are printed in the same two-iteration loop immediately after attachment, before event polling. They are not exit-time link measurements. The source comment describes the intended behavior, but the control flow does not implement it. Rely on actual shutdown observations, not that label, when investigating link loss.

What a missing event cannot prove

Neither a silent tracepoint nor a missing aggregate establishes that no file change happened. An empty map can result from filtering or unsupported syscalls; a path read failure retains only partial evidence; map and transport limits can lose later output. Follow the separatecapture-loss reference when the event is missing after an accepted BPF callback. For reliable after-the-fact outcomes, corroborate observed attempts with return status and the filesystem state rather than treating the presence or absence of a SUMMARY as a complete audit.

  • AgentSight raw syscall dispatcher and aggregate-path selection

  • Root-only mutation runtime fixture and its assertions
  • AgentSight change record: per-syscall hooks to raw_syscalls
  • Linux syscall tracepoint implementation (exact inspected snapshot)

The findings are a code and fixture analysis, not an independent root-kernel runtime reproduction. The particular CI kernel version behind the source-reported missing callbacks was not established from this review. Linux tracepoint ordering can change, and no single current kernel snapshot explains all historical kernels. The master changes have not shipped in the latest reviewed stable release v1.0.35.
